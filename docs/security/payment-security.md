# Payment, Fraud and Account Security\n\n## Security boundary\nThe game server must never trust the client for payment amount, currency, entitlement, balance, shop price, inventory, refund state or withdrawal state.\n\nProduction card processing uses a PCI-compliant payment provider/gateway. The game stores provider-issued customer/payment-method identifiers or tokens and non-sensitive display metadata only. It must never store raw PAN, CVV/CVC, PIN, magnetic-stripe data or full card numbers.\n\nDirect card entry means provider-hosted/tokenized card collection, not a custom server-side card form. A true direct card-processing implementation would materially increase PCI DSS scope and is not the default architecture.\n\n## Supported payment methods\n- PayPal\n- Google Pay\n- debit/credit card through a PCI-compliant gateway/tokenization flow\n- saved payment methods when the provider supports vaulting\n- recurring/automatic payments only after explicit customer consent\n- refunds, chargebacks and disputes\n- webhook-driven entitlement reconciliation\n\n## Payment state machine\nCREATED -> PENDING -> AUTHORIZED -> CAPTURED -> FULFILLED\nFailure paths: PENDING -> FAILED; AUTHORIZED -> VOIDED; CAPTURED -> REFUNDED; CAPTURED -> DISPUTED.\nGame currency/items are granted only after authoritative server-side confirmation of the appropriate provider order/event state.\n\n## Idempotency and replay protection\nEvery payment has an internal order ID, immutable server-generated amount/currency, provider order/payment ID, cryptographically strong idempotency key, creation timestamp, account ID, product/entitlement IDs, status and an audit record.\nRepeated client requests or repeated provider webhooks must not grant currency/items twice. Webhook handlers must verify provider signatures and process events idempotently.\n\n## Authentication and transaction authorization\nSensitive operations require configurable step-up authentication: changing password/email, adding a payment method, first purchase on a new device, high-value purchase, changing automatic-payment settings, withdrawing eligible real-money funds, changing withdrawal destination, or suspicious account recovery.\nSupported authenticators may include passkeys/WebAuthn, authenticator-app TOTP, platform biometrics and provider 3-D Secure/SCA.\nBiometrics unlock a local secure credential; the game does not receive or store biometric data.\nHigh-risk transactions can require re-authentication immediately before authorization. The confirmation screen shows the exact amount, currency, product and destination.\n\n## PayPal\nUse PayPal Orders/Vault APIs and server-side webhooks. Saved PayPal methods are represented by provider tokens/IDs rather than PayPal credentials. Consent is mandatory before future or automatic charges.\nUse PayPal risk/fraud capabilities and collect provider-required risk signals. Verify webhook signatures before fulfillment.\n\n## Google Pay\nUse Google Pay as a tokenized payment method through a supported payment gateway/processor. The client obtains the payment token and sends it to our backend; the backend sends it to the processor.\nDo not implement Google Pay DIRECT decryption unless the business deliberately accepts the additional PCI DSS infrastructure and assessment requirements.\n\n## Cards\nCard collection uses the payment processor's hosted fields/checkout or equivalent tokenization mechanism.\nNever log or persist PAN, CVV/CVC, card PIN, track data or payment authentication secrets.\nStore only provider customer ID, provider payment-method token/ID and permitted non-sensitive display metadata such as brand and last four digits.\n\n## Automatic payments\nAutomatic payments are opt-in. The UI states amount or pricing rule, currency, frequency/trigger, next expected charge when determinable, payment method and cancellation method.\nThe user explicitly authorizes the mandate/consent through the provider-supported flow.\nAutomatic charges are performed server-side using the provider's vaulted payment method. The client cannot trigger an arbitrary amount.\nAccounts provide enable/disable automatic payments, payment history, saved-method revocation and automatic-payment authorization revocation.\n\n## Fraud controls\n- per-account velocity limits\n- per-payment-method velocity limits\n- IP/device risk signals\n- failed-payment thresholds\n- rapid account/payment-method changes\n- abnormal purchase velocity\n- bot/card-testing detection\n- new-device risk\n- account-age risk\n- high-value transaction step-up\n- repeated chargeback/dispute monitoring\n- duplicate-order detection\n- inventory/currency anomaly detection\n- administrator audit trails\nProvider fraud tools are preferred over attempting to recreate card-network fraud detection.\n\n## Shop abuse protection\nShop purchases use server-authoritative catalogue prices and atomic transactions. The client cannot set prices, set gold balances, grant items, replay purchases, alter product IDs after authorization, submit negative quantities or overflow balances.\nAll real-money amounts use integer minor units or another exact monetary representation. Floating-point arithmetic must not determine real-money amounts.\n\n## Withdrawal / cash-out security\nIf a future feature allows players to withdraw real money, it is a separate regulated financial subsystem, not a reverse shop purchase.\nBefore enabling it, implement eligibility checks, KYC/age/jurisdiction requirements where legally required, sanctions/AML screening where applicable, verified withdrawal destination, step-up authentication, limits, velocity controls, fraud review, cooling-off periods for newly changed payout destinations, immutable withdrawal ledger, double-entry accounting, provider payout reconciliation, manual review/hold states and a complete audit trail.\nNo withdrawal is fulfilled solely because the client reports success.\n\n## Secrets and audit\nPayment API credentials, webhook secrets and encryption keys are never stored in source control. Production secrets are separated from development/test secrets and rotated.\nPayment audit events include event ID, account ID, order ID, provider event ID, event type, timestamp, outcome, risk decision, actor/source and correlation ID. Sensitive payment credentials never enter logs.\n\n## Incident response\nMonitor payment webhook signature failures, duplicate webhook IDs, unusual purchase bursts, repeated payment failures, impossible entitlement grants, currency anomalies, withdrawal anomalies, account takeover indicators and repeated authentication failures.\n\n## Principle\nThe mobile client is an untrusted presentation layer. The server, database transaction boundaries and payment provider are authoritative.
